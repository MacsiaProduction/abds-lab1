# ЭнергоСбыт: лабораторная №1

Kotlin/JVM-сервис без авторизации для учебной модели ЖКХ. Один ClickHouse 26.7, семь таблиц, девять HTTP-операций. Справочник API с примерами запросов и ответов: [api/openapi.json](api/openapi.json).

## Запуск

Нужны Docker или существующая VM Podman, Compose и доступ к официальным архивам Oracle JDK и Maven Central. Системные Kotlin и Gradle для запуска через Docker не нужны. Настройки и публичные учебные учётные данные находятся в `.env.local`; файл включается в репозиторий. Секреты в него добавлять нельзя.

```sh
make run
make setup
curl http://localhost:8080/ping
curl http://localhost:8080/users/1
make teardown
make stop
```

Для Podman можно выбрать движок без изменения Docker-настроек системы:

```sh
export CONTAINER_ENGINE='podman --connection podman-machine-default-root'
make run
make setup
```

Путь и имя подключения должны соответствовать вашей уже существующей VM; Makefile не создаёт и не запускает новые VM. Без этой переменной используется Docker, как в CI курса.

`make run` собирает приложение, запускает сервисы и ожидает готовности ClickHouse. `make setup` создаёт схему, генерирует CSV и загружает их пакетами по 100 000 строк. `make gen` работает без запущенной базы. `make load` требует созданной пустой схемы; после частичной или полной загрузки нужно явно выполнить `make teardown && make setup`. Повторный load отказывается писать в непустую базу, потому что VersionedCollapsingMergeTree не обеспечивает идемпотентность повторного CSV.

**`make teardown` удаляет всю базу, указанную в CLICKHOUSE_DATABASE.** Используйте только отдельную учебную базу. Сгенерированные CSV можно оставить для проверки; gen перезаписывает их детерминированно. `data/` и `volume/` исключены из Git и Docker build context.

Все параметры подключения берутся из `.env.local`. Хостовые проверки используют `CLICKHOUSE_HOST=localhost`, приложение внутри Compose — `clickhouse`. Порты сервера ClickHouse читаются из тех же переменных через `docker/ports.xml`; XML содержит только ссылки на env, не отдельные значения. Временная зона — UTC. Изменение настроек существующего ClickHouse volume может потребовать чистой учебной базы.

## Сборка и проверки без ClickHouse

Нужен JDK 27. Gradle wrapper закреплён на 9.9.1 с SHA-256. Kotlin 2.4.21 выпускает байткод JVM 26; Java target согласован с ним. Дистрибутив запускается на JDK 27. Версии библиотек: `gradle/libs.versions.toml`, resolved-версии — `gradle.lockfile`, SHA-256 артефактов — `gradle/verification-metadata.xml`. Для SnakeYAML закреплена совместимая версия 4.0.1: новейшая 5.0.0 вызывает NoSuchMethodError при разборе YAML через Kaml 0.104.0. Это проверяемое исключение из выбора последних стабильных версий.

```sh
./gradlew check installDist
./gradlew ktlintFormat
```

Тесты проверяют API и SCD-переходы с поддельным хранилищем, SQL-транспорт через HTTP-сервер и генерацию полного датасета без ClickHouse. Для проверки на настоящей базе после свежего setup выполните:

```sh
python3 scripts/e2e.py
```

Скрипт изменяет учебные записи; для восстановления выполните `make teardown && make setup`. В Podman на linux/arm64 прошли 35 тестов, 33 проверки автогрейдера, API/SCD/DELETE и проверки восстановления. Генерация с загрузкой заняла около 4 секунд при 4 CPU и 8 ГБ RAM. GitHub Actions и Linux/amd64 пока не проверены.


## Схема и данные

Схема — `src/main/resources/schema.sql`. Имена, типы и движки соответствуют заданию. Ключи:

| Таблица | ORDER BY | Причина |
|---|---|---|
| dim_realty, dim_gauges | id | Чтение по идентификатору |
| dim_users | id | Одна актуальная версия собственника |
| dim_tariffs | (id, valid_from) | Сохраняем интервалы SCD2 одного тарифа |
| fact_meter_readings | (realty_id, reading_date) | Корректировка заменяет значение объекта за дату, включая смену связанных ID |
| fact_gauge_bindings | (realty_id, gauge_id) | Отмена имеет исходный ключ и версию; новая установка — следующую версию |
| fact_invoice | (realty_id, created_at) | Счета объекта в порядке времени |

Партиционирование не добавлено: объём учебный, отдельного жизненного цикла партиций нет. Нельзя включать sign или время отмены в ключ привязки. Для текущих значений используется FINAL; OPTIMIZE не требуется для корректности API.

Генератор использует только синтетические данные и фиксированные правила:

- 1 000 объектов в нескольких домах, в том числе нежилые; 1 000 собственников.
- 1 100 счётчиков и 1 200 строк привязок. Первые 100 объектов меняют счётчик 1 ноября 2025 года.
- Два смежных интервала тарифа: до 1 ноября 2025 года — 500/250 копеек, после — 620/310. Открытый конец — 2099-01-01.
- 1 096 000 актуальных показаний за 2023-11-01…2026-10-31 и 32 880 дополнительных строк корректировок (3%). Всего физических CSV-строк показаний — 1 128 880.
- 36 000 счетов: объект × 36 месяцев. Потребление считается по разностям накопительных показаний с нулевым начальным уровнем, при замене счётчика уровень сбрасывается. Корректировка восстанавливает итоговое значение, по которому рассчитан счёт. Срок оплаты — десятое число следующего месяца.

В одном месячном счёте один счётчик и один тариф: изменения запланированы на начало месяца. Деньги — целые копейки. Сервис не создаёт счета через HTTP и не пересчитывает сохранённые счета по сегодняшнему тарифу.

## SCD-сценарии

Ниже команды для ручной проверки. Эти сценарии также проверяет `python3 scripts/e2e.py` после свежего setup; скрипт изменяет только синтетические учебные записи. Штатный автогрейдер курса запускается отдельно. Примеры команд используют Docker; с Podman замените движок на выбранное подключение. Для SQL можно использовать:

```sh
docker compose --env-file .env.local exec clickhouse sh -c 'clickhouse-client --port "$CLICKHOUSE_PORT" --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" --database "$CLICKHOUSE_DATABASE"'
```

### ФИО и телефон

```sh
curl -i -X PATCH localhost:8080/users/1 -H 'Content-Type: application/json' -d '{"fio":"Новое имя"}'
curl -i -X PATCH localhost:8080/users/1 -H 'Content-Type: application/json' -d '{"phone":"+79111111111"}'
curl -i -X PATCH localhost:8080/users/1 -H 'Content-Type: application/json' -d '{"phone":"+79222222222"}'
curl localhost:8080/users/1
```

```sql
SELECT fio, phone, phone_prev FROM dim_users FINAL WHERE id = 1;
```

Ожидаются новое ФИО, последний и предпоследний телефон. ФИО SCD1 исчезает из текущего логического состояния; старые физические строки могут существовать до фонового слияния. Требование физического стирания нельзя доказать одним FINAL. Повторная передача того же телефона не меняет phone_prev.

### Тариф и исторический счёт

```sh
curl 'localhost:8080/tariffs?date=2025-10-31'
curl 'localhost:8080/tariffs?date=2025-11-01'
```

```sql
SELECT id, price_day_kwph, valid_from, valid_to FROM dim_tariffs FINAL ORDER BY id, valid_from;
SELECT created_at, day_kw, night_kw, price FROM fact_invoice WHERE realty_id = 1 ORDER BY created_at;
```

На границе возвращаются разные интервалы. Для старого счета проверьте `price = day_kw * 500 + night_kw * 250`, для нового — `day_kw * 620 + night_kw * 310`. Использование текущей цены не изменяет сохранённую историческую сумму.

### Корректировка показания

```sh
curl -i -X POST localhost:8080/realty/1/readings -H 'Content-Type: application/json' -d '{"user_id":1,"gauge_id":1,"tariff_id":1,"reading_date":"2026-10-01","day_kw":1250,"night_kw":300}'
curl 'localhost:8080/realty/1/readings?date_from=2026-10-01&date_to=2026-10-01'
```

```sql
SELECT * FROM fact_meter_readings FINAL WHERE realty_id = 1 AND reading_date = '2026-10-01';
```

Ожидается одна актуальная строка с новыми значениями. До слияния исходная и корректирующая физические строки могут существовать одновременно.

### Замена счётчика

```sh
curl -i -X POST localhost:8080/realty/1/gauges -H 'Content-Type: application/json' -d '{"gauge_id":2}'
```

```sql
SELECT * FROM fact_gauge_bindings FINAL WHERE realty_id = 1;
```

Ожидается только новая активная установка. Отмена копирует прежний ключ, версию и created_at с противоположным sign; новая запись получает version + 1. Если активной установки не было, новая версия равна 1.

### Удаление ошибочной строки

На отдельной учебной базе после проверки исходных объёмов:

```sql
INSERT INTO fact_invoice (realty_id,user_id,tariff_id,gauge_id,day_kw,night_kw,price,deadline,created_at)
VALUES (999999999,1,1,1,10,1,9999990,'2026-11-10','2026-10-31 12:00:00');
SELECT count() FROM fact_invoice WHERE realty_id = 999999999;
ALTER TABLE fact_invoice DELETE WHERE realty_id = 999999999 SETTINGS mutations_sync = 1;
SELECT count() FROM fact_invoice WHERE realty_id = 999999999;
```

Ожидается 1 до удаления и 0 после синхронной мутации. Частые изменения API используют версии, а не такие мутации.

## Ограничения и восстановление

Мутации сериализуются одним coroutine Mutex в единственном процессе приложения. Для DateTime-версий следующий timestamp строго больше предыдущего: при двух быстрых изменениях одного объекта сервис ждёт следующую секунду. Если часы не продвинулись за 5 секунд, операция завершается ошибкой. После рестарта предыдущая версия читается из базы. Несколько экземпляров приложения этим mutex не защищаются.

Отмена и новая привязка отправляются одним INSERT. Автоматических повторов INSERT после неизвестного сетевого результата нет: ответ об ошибке не является доказательством отсутствия записи. Проверьте состояние перед ручным повтором; для воспроизводимого восстановления учебного датасета используйте teardown/setup.

SQL-проверки свежего датасета находятся в `sql/checks.sql`; интеграционный скрипт выполняет их до изменений через API. Повторная загрузка и цикл teardown/setup проверены отдельно.

`.github/` и CODEOWNERS сохранены из шаблона. Перед сдачей нужны эффективная защита основной ветки, доступ преподавателя, успешный CI и отправка PR через форму пользователем. Репозиторий GitHub, PR и настройки доступа автоматически не создавались.
